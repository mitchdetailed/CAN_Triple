# Programming a CAN Triple (STLINK-V3MINI)

Every CAN Triple is programmed and debugged with an **STLINK-V3MINI**. This folder holds
the single source of truth for how PlatformIO talks to that probe, plus a script that
pushes it into every project.

## The problem this solves

PlatformIO's `ststm32` platform hardcodes the OpenOCD invocation for ST-Link:

```
-f interface/stlink.cfg -c "transport select hla_swd"
```

`hla_swd` belongs to OpenOCD's **legacy HLA driver**, which is being retired. What
`interface/stlink.cfg` does depends on the OpenOCD version PlatformIO happens to have
installed on that machine:

| OpenOCD (`tool-openocd`)      | `interface/stlink.cfg` selects | Working SWD transport                 |
| ----------------------------- | ------------------------------ | ------------------------------------- |
| 0.11.x (`2.1100.x`) and older | `hla` driver                   | `hla_swd`                             |
| 0.12.0+dev (`3.1200.x`)       | `st-link` DAP driver           | `swd` (`dapdirect_swd` deprecated)    |

So on an up-to-date machine every upload and debug session dies with:

```
Error: Debug adapter doesn't support 'hla_swd' transport
```

while an older machine keeps working — which is exactly the "some machines work, some
don't" split. Pinning one transport in `platformio.ini` only moves the breakage to the
other half of the machines.

## The fix

The ST-Link tool is now defined by the **board file** (`boards/CAN_Triple.json`) instead
of being generated by the platform, and it chooses the transport at runtime:

```json
"debug": {
  "tools": {
    "stlink": {
      "default": true,
      "onboard": true,
      "server": {
        "package": "tool-openocd",
        "executable": "bin/openocd",
        "arguments": [
          "-s", "$PACKAGE_DIR/openocd/scripts",
          "-f", "interface/stlink.cfg",
          "-c", "if {[catch {transport select swd}]} { if {[catch {transport select dapdirect_swd}]} { transport select hla_swd } }",
          "-f", "target/stm32g4x.cfg"
        ]
      }
    }
  }
}
```

The Tcl line tries `swd` (new OpenOCD), falls back to `dapdirect_swd` (OpenOCD 0.11
DAP driver), then to `hla_swd` (OpenOCD 0.11 HLA driver). The first one the local
OpenOCD accepts wins, so the same file works on every machine, old or new.

Defining it on the board — rather than with `debug_server` in `platformio.ini` — means
**upload and debug take the identical path**: `pio run -t upload` reads
`debug.tools.stlink.server.arguments` too, and the platform leaves the block alone
because it is already present.

`platformio.ini` therefore only needs the shared three lines, the same in every project:

```ini
board = CAN_Triple
upload_protocol = stlink
debug_tool = stlink
```

Do **not** add `debug_server` or `upload_command` back into a `platformio.ini`; those
override the shared definition for one project only and reintroduce the split.

## Shared files

This folder is the single source of truth for two files that every project needs to
have in common. The sync script copies them in:

| Canonical file in this folder | Copied to each project as | Purpose                                    |
| ----------------------------- | ------------------------- | ------------------------------------------ |
| `CAN_Triple.json`             | `boards\CAN_Triple.json`  | Board + the ST-Link upload/debug definition |
| `build_flags.py`              | `scripts\build_flags.py`  | Pre-build script that enables float printf/scanf |

`build_flags.py` prints plain ASCII on purpose. It used to print emoji, which crashes
the build with `UnicodeEncodeError: 'charmap' codec can't encode character '✅'`
whenever PlatformIO's output is not UTF-8 — redirected output, CI, or a console on a
non-UTF-8 code page. That failure looks nothing like an encoding problem in the log, so
keep the output ASCII.

## Using the sync script

```powershell
# push the canonical files into every project under CAN_Triple\Projects
python "Programming Tools\sync_programming_config.py"

# verify only - exits 1 if any project drifted (good for a pre-commit / CI check)
python "Programming Tools\sync_programming_config.py" --check

# report what this machine will actually do
python "Programming Tools\sync_programming_config.py" --doctor

# also cover the CAN Triple projects that live outside this repo
python "Programming Tools\sync_programming_config.py" --root "C:\Users\<user>\Desktop\Claude Code"
```

`--root` is repeatable and defaults to this repository. It reaches the projects kept
outside `CAN_Triple` — `development-of-cantriple`, the `Claude Code` root project and
the `CAN Triple GUI Vibecoding*\firmware` folders — so one command keeps everything on
the same programming setup.

**Custom board files are preserved.** If a project's `boards\CAN_Triple.json` differs
from the canonical one for a real reason (the GUI firmware caps `maximum_size` at
65536 for its dual-bank linker script), the script only injects the shared
`debug.tools.stlink` block and leaves the rest of that file alone. Identical board
files are replaced wholesale.

`--doctor` prints the installed `tool-openocd` version, whether its `stlink.cfg` is the
HLA or DAP flavour, and runs OpenOCD against the shared config to show the transport it
lands on — without touching the hardware. Example, on a machine with new OpenOCD:

```
package : C:\Users\<user>\.platformio\packages\tool-openocd
version : 3.1200.7
stlink.cfg: ST-Link DAP -> this machine needs 'swd'
transport : swd (dapdirect) (selected by the shared board config)
```

To change anything about programming (speed, reset behaviour, a different probe), edit
`Programming Tools\CAN_Triple.json` and re-run the script — never edit a project's
`boards\CAN_Triple.json` or `scripts\build_flags.py` directly, they are overwritten.

## Applying it on another machine

Pull the repo. Nothing else is required — no OpenOCD downgrade, no per-machine tweaks.
If a machine still fails, run `--doctor` first; it identifies the toolchain in one shot.

## Optional: pin the toolchain as well

The config above is version-agnostic on purpose, so pinning is not required. If you
would rather have every machine run byte-identical tools, pin the platform in each
`platformio.ini` (this forces a one-time download on machines that are behind):

```ini
platform = ststm32@17.0.0
```

## Troubleshooting

| Symptom                                             | Cause / fix                                                                                   |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `Debug adapter doesn't support 'hla_swd' transport` | Project still has an old board file — run the sync script.                                     |
| `Error: open failed`                                | No probe enumerated: check the USB cable/driver, and that the STLINK-V3MINI shows as VID 0483. |
| `Error: init mode failed (unable to connect to the target)` | SWD wiring/target power, or the target is held in reset. Drop `debug_speed` to `4000` to test. |
| Upload works, `pio debug` does not                  | A leftover `debug_server` line in that project's `platformio.ini` — remove it.                  |
| `UnicodeEncodeError: 'charmap' codec can't encode…` | A build script printed a non-ASCII character — run the sync script to restore `build_flags.py`. |
| Probe found but flashing is flaky                   | Update the STLINK-V3MINI firmware with ST's `STM32CubeProgrammer` / `STLinkUpgrade`.            |
